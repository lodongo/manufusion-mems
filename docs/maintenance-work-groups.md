# Maintenance Work Groups — controlled introduction

The work group is a site-level operational team, not a new cost center or financial posting object. One cost center has one work group. An employee may hold multiple generic titles, but only an existing current position assignment covering the relevant cost center qualifies. Draft configuration is restricted to workflow administrators, version checked, audit logged, and does not grant any operational access.

## Cutover release gates (not enabled by this change)
- Generate location-bound permissions from the intersection of active work group, cost center, mapped task, named incumbent, and current organizational assignment. Preserve ordinary employee request rights. Never broaden procurement, finance Chart of Authority, safety, handover or stores authorities.
- Resolve each workflow gate against the equipment's work group rather than the current global approverRoles setting. Distinct gate codes sharing a permission must not inadvertently grant the other transition.
- Replace single-position WR reviewer queue, automatic routing, named reviewer validation, assessment approval snapshots, asset task validation and all work order/window authority checks. Existing under-review and approved items need a controlled revalidation/reassignment path; never silently invalidate finalized history.
- Preserve the independently enforced requester/reviewer, assessor/approver, planner/cost approver, performer/verifier, and technical closure checks. A generic title is never a substitute for a different authenticated UID. Test administrators and direct/wildcard legacy security roles for bypasses.
- Independent maker/checker approval to publish configuration; versioned rollback and audit history. Include changes in window fingerprints and role approval snapshots. Simulate every assigned task and negative path before enabling. Fail closed for missing or ambiguous scope, revoked or expired assignment and stale config at an activated cost center.
- Test tenant/site separation, concurrent edits, repeated roles/titles, staffing vacancies, stale approvals, exact gate permission, and independent external authorities.

The Work Groups screen clearly marks saved records as drafts. Current workflow configuration remains authoritative. No migration or activation is performed in this change.

## Planner resource pool and numbering
New groups receive an immutable tenant-wide WG_0001-style sequence from a database counter committed atomically with the group. Existing codes are retained; the next number is above any existing sequence. Saved groups (including draft role mappings) identify planning resources but grant no security authority. The planner sees the work order cost center’s group by default. The server independently requires an explicit per-allocation outside-group opt-in; when no group is configured every employee is outside the group. The allocation records the group revision and outside employee IDs. Existing competency, scope, maker/checker and execution gates remain in force.

## Master versus group configuration
Master setup is organization-wide and versioned: generic titles → organizational positions, and workflow activities → generic titles. New group identities (name, site, automatic number) are created only in Master setup. The default page lists groups; each group contains cost centers and named incumbents only, and reads inherited task mappings. A UID may appear under multiple aligned titles in one group, but may not belong to another group; a cost center also belongs to exactly one group at a time. Server validation serializes changes, checks current master and group revisions, and rejects cross-group duplicates. Legacy draft mappings are offered as explicit suggestions on first setup rather than silently expanded into permissions; existing group records are preserved. Conflicting legacy employees are not included in the default planner resource pool until resolved. No changes to operational workflow security cutover are made.

## Active workflow policy
Saved drafts may be incomplete; existing live snapshots remain unchanged. A different administrator approves saved master and selected group revisions using the Approve & activate tab. The active snapshot is organization-wide, versioned and published atomically. Managed activity permissions and gate checks use the named employee, current HR assignment, aligned actual role, group cost centers and approved revision; legacy/wildcard permissions do not override managed actions at activated locations. External Safety, Operations handover and Finance procurement authority remains unchanged. Unactivated locations use legacy authority. Cutover requires draining affected open requests/orders; it does not silently migrate or invalidate already-approved historical records. Outside-group execution is restricted to explicitly allocated tasks and current aligned execution roles. Operator is included in request and allocated execution defaults. Partial drafts never grant new security rights.

Publication revisions are scoped: adding a group under an unchanged master does not invalidate other unchanged groups' approval tokens. Current active snapshots remain in effect when an incomplete revision is saved.

## Development test override
The authenticated organization super admin can activate incomplete, saved Work Group configurations and bypass independent checker and open-transaction cutover prerequisites while the platform's tenant-specific, time-limited development test mode is active. Invalid site/cost-center references, duplicate group assignments and revision conflicts remain blocked. Empty groups confer no location grants. Override approval records retain the skipped rules, warnings and affected open transactions; the high-priority activation audit is atomic with publication. Existing transactions are not deleted or automatically reapproved and may need normal approval/window revalidation. Named-role authorization can be relaxed for the test-mode super admin; normal users remain governed by the approved snapshot. General test-mode bypass audit events carry high priority, individual controls and action context.

### Inherited organizational roles in group staffing
The Named employees tab renders every aligned organizational role directly from the saved master configuration, including multiple roles under the same generic title. Role alignment is read-only in group setup. Each inherited role has its own employee picker, filtered to eligible holders at the group's scope and excluding employees already assigned to another group. Changes to master alignment require a reload before saving the group; existing server-side assignment, duplicate and version checks are unchanged.

## Current responsibility
Requests, assessments, orders, windows and task validation derive current group and responsible candidates on read. New records and regular updates snapshot active group metadata. Candidate names are calculated from current HR assignments, active group task mappings and independence checks. Existing assigned request reviewer is retained; otherwise highest position in reporting hierarchy appears first, followed by generic-role seniority and name. Finance, safety and handover retain separate authority. Draft or unassigned locations do not grant authority.

New work requests cannot be submitted at an unassigned cost center once the organization has activated Work Groups, except through the audited development test override. Existing ungrouped transactions retain transitional legacy permissions; no incomplete group draft grants rights. Revoked request reviewer assignments resolve to a current eligible named holder on refresh; the next successful workflow mutation persists the reassignment and audit record.

### Responsibility diagnostics and actual titles
Responsibility display resolves actual organizational job titles from the active alignment even when no employee is eligible. It explains missing role alignment, named assignments, maker-checker conflicts, invalid scope, and conflicting gate/security activity allocations rather than displaying generic unassigned roles. When saved master or group revisions differ, it displays a clearly marked read-only preview of the saved job title and employee, without granting new rights. The existing independently approved activation remains authoritative. Work Group Master Setup shows the actual titles for each task and configuration overlap warnings.

One-to-one task gate and security activity allocations are linked on explicit edits in Master Setup, including server-side synchronization for API clients. Existing inconsistent pairs remain visible for intentional resolution, avoiding unapproved live authorization changes. Shared permissions and independent authorities are not automatically merged.

### Work request direct closure attribution
The Closed by picker lists only named, currently eligible members of the active Work Group mapped to MNT.WO.execute. The same resolver rechecks the submitted employee on the server under the maintenance mutation lock. The credited employee's actual job-title snapshot and the separate signed-in reviewer identity are saved; Test Mode never broadens employee attribution. When an organization has Work Groups setup but no active group at that location, activation is required. Pre-Work-Group installations retain only the independently configured legacy executor role at the record location, not the full employee directory.

Both direct closure flows (including legacy supervisor-confirmed requests) require an actual completion date and positive whole-minute duration. These are stored in the closure and retained through confirmation or rejection history, separately from the automatic recording/approval timestamps. Existing historical records are not rewritten.

## Retrospective Work Orders from request closure
A direct closure declares no spares or external services, records actual maintenance classification, executor, date and minutes. Current requests close atomically with one linked Work Order. Legacy supervisor-confirmed requests create the order when independent confirmation is saved. Earlier historical closures are not backfilled. The order carries an actual-work task rather than a manufactured approved assessment or schedule. The named performer confirms technical feedback and the no-resource declaration; original reported minutes are preserved. Safety sign-off, Operations handover and independent technical closure remain required. Existing incident controls apply. Planning, resource transactions and window scheduling are blocked. Labour valuation remains pending when no approved rate exists.

## Order-first workflow and coded operational state
New requests use reviewer Close or Confirm. Confirmation atomically allocates a WO number and creates an order in WO010 before assessment. Existing standalone assessment documents remain readable and convertible. The operational state is derived from the earliest outstanding prerequisite, with spares ahead of services, specialists and labour; it is separate from the coarse transaction flags used by permission and execution guards. State transitions are appended with actor, source and UTC timestamp. Maintenance mutations recalculate the state and reads reconcile live procurement, reservation, cost and window evidence; externally changed state is timestamped when observed on refresh, not backdated. External specialist availability requires explicit provider, reference, headcount and evidence before readiness. No independent approval or safety gate is auto-approved.

The Work Assessments register additionally routes new order-first assessment tasks to the Work Order itself. Technical classification (evaluation, failure mode, severity, solution, maintenance type and priority) remains part of the assessment and must precede approval. Procurement/PO and Finance cost-decision mutations attempt immediate linked-state reconciliation; refresh is the safety net if an external hook fails or a source is updated outside these routes.

## Weekly maintenance cycle and status review
Global Work Groups Master setup includes an independently versioned and audited weekly cycle start day and IANA timezone. Monday is the default; organization timezone or UTC fallback. New order-first confirmations require a maintenance type, start and end dates. MAI-001/002/003/004/008/009/010/011/013/014/015 require the following maintenance cycle or later; other types may start today. The rule applies to newly admitted dates, not repeatedly to orders already accepted into their scheduled cycle. Legacy standalone-assessment conversion retains its previous date rule. Retrospective orders record actual completion dates and are exempt from forward planning. Changes require validation and retain date history. New maintenance window tasks must fall within the corresponding order dates. The default Status review tab shows readiness, distinct task/activity progress, observed waiting and overdue state dwell charts, estimated versus recorded costs and time, and transition history. Unclassified historical time is not attributed to invented stages; cost commitments are not treated as ledger actuals.
